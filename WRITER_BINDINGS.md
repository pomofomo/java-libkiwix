# LIBZIM.md – Add ZIM writer bindings to java-libkiwix

Instructions for a Claude Code session. They are self-contained: read them fully before starting.

## Goal

Add Java/Kotlin bindings for libzim's **ZIM writer** (`zim::writer::Creator`) to [kiwix/java-libkiwix](https://github.com/kiwix/java-libkiwix), in our fork. The work has two outcomes:

1. **Upstream PR:** a clean, reviewable pull request to `kiwix/java-libkiwix` that matches the project's style, build and tests.
2. **wyz build:** a published artifact from the fork that wyz uses until upstream merges and releases the feature.

**Why:** wyz is a Kotlin Multiplatform app (desktop JVM + Android) whose desktop builder writes ZIM files: per-page HTML, WebP diagrams, standard and custom `X-Pack-*` metadata, an illustration, and full-text and title indexes. See SPEC.md §4 in the wyz repo. java-libkiwix only *reads* ZIMs today, and no other JVM ZIM writer exists. python-libzim works but would mean shipping Python with the desktop app. zimwriterfs can't write custom metadata.

## How the existing bindings work (follow this pattern exactly)

- **Java side:** `lib/src/main/java/org/kiwix/libzim/*.java`.
  - Each class has `native` methods and a `private long nativeHandle`.
  - It has `public native void dispose()` and `finalize()` that calls `dispose()`.
  - Constructors call a native `setNative…` method (see `Archive.java`).
- **C++ side:** `lib/src/main/cpp/libzim/*.cpp`, one per Java class.
  - Each file defines `CLASSNAME`, `NATIVE_TYPE` and `TYPENAME` (e.g. `libzim_Archive`), then includes `macros.h`.
  - Methods use the `METHOD0`, `METHOD`, `GETTER` and `DISPOSE` macros, each ending with `CATCH_EXCEPTION(ret)`.
- **Native handle:** `utils.h` stores a heap-allocated `shared_ptr<NATIVE_TYPE>` in `nativeHandle` (`SET_PTR`, `getPtr`, `dispose`).
  - Conversions: `TO_C(jstring)`, `TO_JNI(x)`, `cArray2jni`, `buildWrapper`.
  - Errors: `throwException(env, "java/class/Name", msg)`.
- **JNI headers:** generated by `./gradlew buildHeaders` (`javac -h`). Every new Java file must be added to `getLibzimFiles()` in `lib/build.gradle`.
- **Native library:** each new `.cpp` must be added to `add_library(zim_wrapper SHARED …)` in `lib/src/main/cpp/CMakeLists.txt`. On Linux it links the imported `libzim.so`. On Android it links per ABI and loads through `JNIKiwix` (ReLinker).
- **Tests:** plain JUnit 4 in `lib/src/test/org/kiwix/test/libzim/`.
  - They run on the Linux JVM through `./gradlew runTests`, with `-Djava.library.path=build`.
  - Test ZIMs are made by `lib/src/test/create_test_zimfiles` (zimwriterfs).
  - CI (`.github/workflows/ci.yml`) runs `install_deps.sh`, then `./gradlew buildHeaders build`, then the coverage report.
- **Known pitfall (string encoding):**
  - `jni2c<std::string>` uses `GetStringUTFChars`, which returns *modified* UTF-8. Characters outside the BMP (emoji, some CJK) and NUL come out wrong.
  - For every writer string that matters (paths, titles, metadata, content), pass UTF-8 bytes from Java (`s.getBytes(StandardCharsets.UTF_8)` → `jbyteArray`) or add a correct conversion helper.
  - Add a round-trip test with emoji and CJK.
  - Fixing the reader-side helper is a separate, optional upstream PR; don't mix it in.

## libzim writer behaviour you must respect

Verified in libzim 9.8.2 source:
- **Temp file handling:**
  - `startZimCreation(path)` writes to `path + ".tmp"`, and `finishZimCreation()` renames it to `path`.
  - Destroying a `Creator` that was never finished removes the `.tmp` file (`CreatorData::~CreatorData`).
  - So **disposing without finishing must leave nothing behind.** Keep it that way and test it. Do **not** copy python-libzim's `__exit__`, which always calls finish, even after an exception.
- **Threading:**
  - `addItem` calls `item->getContentProvider()` on the caller's thread.
  - `ContentProvider::feed()` is called later from libzim's cluster-writing code, potentially on worker threads.
  - Index data may also be pulled outside the caller's thread.
  - So any Java-implemented `Item`/`ContentProvider` would be called from native threads. That needs `AttachCurrentThread`, global refs and careful exception handling.
- **Thread safety:** the `Creator` itself is not thread-safe. Calls must come from one thread; document this in Javadoc.
- **Errors:** worker errors surface on later calls via `checkError()`, which throws `zim::CreatorStateError` and similar.
  - Read `include/zim/error.h` and map each writer exception to a Java exception.
  - Add a `ZimCreatorException` (or reuse `java/lang/Exception` as upstream does), then extend `CATCH_EXCEPTION` or add a writer-specific catch macro.
- **Hints:** `zim::writer::Hints` is `std::map<HintKeys, uint64_t>` with `COMPRESS` and `FRONT_ARTICLE`.
- **UUID:** `setUuid(const zim::Uuid&)` exists in C++. Expose it; python-libzim doesn't.

## Proposed Java API (package `org.kiwix.libzim.writer`)

```java
public class Creator implements AutoCloseable {
  public Creator();                                         // native: new zim::writer::Creator
  public Creator configVerbose(boolean verbose);
  public Creator configCompression(Compression c);          // enum Compression { NONE, ZSTD }
  public Creator configClusterSize(long bytes);
  public Creator configIndexing(boolean indexing, String language);   // ISO 639-3, e.g. "eng"
  public Creator configNbWorkers(int n);
  public void startZimCreation(String path);
  public void setMainPath(String path);
  public void setUuid(byte[] uuid16);                       // exactly 16 bytes
  public void addItem(Item item);                           // StringItem | FileItem (phase 1)
  public void addMetadata(String name, String content);                   // text/plain;charset=utf-8
  public void addMetadata(String name, byte[] content, String mimetype);
  public void addIllustration(int size, byte[] png);        // 48 → Illustration_48x48@1
  public void addIllustration(IllustrationInfo info, byte[] content);     // reuse existing org.kiwix.libzim.IllustrationInfo
  public void addRedirection(String path, String title, String targetPath, Map<Hint, Long> hints);
  public void addAlias(String path, String title, String targetPath, Map<Hint, Long> hints);
  public void finishZimCreation();
  @Override public void close();                            // = dispose(); unfinished → no file left
  public native void dispose();
}

public enum Hint { COMPRESS, FRONT_ARTICLE }

public abstract class Item { /* sealed in practice: only the classes below in phase 1 */ }
public final class StringItem extends Item {
  public StringItem(String path, String mimetype, String title, Map<Hint, Long> hints, byte[] content);
  public StringItem(String path, String mimetype, String title, Map<Hint, Long> hints, String content);
}
public final class FileItem extends Item {
  public FileItem(String path, String mimetype, String title, Map<Hint, Long> hints, String filePath);
}
```

Design notes:
- **Builder-style config:** the config methods return `this`, like C++ and python-libzim. Calling config after `startZimCreation` throws `IllegalStateException`.
- **After finish:** any call after `finishZimCreation()` throws `IllegalStateException`.
- **Phase 1 has no Java callbacks.** `StringItem` and `FileItem` map straight to libzim's `StringItem::create` and `FileItem`, so no native thread ever calls into the JVM. The default HTML indexer extracts title and content from `text/html` items.
- **Phase 2 (optional, separate PR):** a user-subclassable `Item` with `getContentProvider()`/`getIndexData()` implemented in Java. This needs a native trampoline class holding a `GlobalRef`, attaching worker threads (`AttachCurrentThread`/`DetachCurrentThread`), and turning Java exceptions into C++ exceptions that libzim reports through `checkError()`. Only do this if maintainers want it; wyz doesn't need it.
- **Kotlin-friendly:** the API is plain Java, so `Creator().use { … }` works from Kotlin.
